## What Doesn't Work — antipatterns & mistakes

- Never make GitLab quick-action safety depend on predicting which lines GitLab renders as code. GitLab deletes `\r`, renders with comrak plus GLFM extensions (`>>>` multiline quotes, `: ` description lists, alerts), then runs `^\/cmd` on the source lines of top-level paragraphs. A line heuristic and commonmark.js both mis-modelled `>>>\n~~~\n>>>\n/close`, so `/close` ran as the service account (30 bypasses in a 59,904-body comrak fuzz). The fix is context-independent: neutralise EVERY command-shaped line, with `\/` outside code and U+200B inside code, so a wrong parse only affects rendering. Evidence: server/src/modules/pulls/comment-body.ts (`neutraliseQuickActions`, PR #15); server/test/comment-body.test.ts. Confidence: high. (2026-10-20)
- Never audit a mutation from the route's HTTP status when the route can fail softly. Settings test-connection answers 200 `{ok:false}` when the key save fails, so the old `secret.save` route descriptor logged saves that never happened. Write the audit row in the service, inside the same transaction as the write (`SettingsService`). Evidence: server/src/modules/settings/service.ts; server/test/auth-guard-matrix.test.ts. Confidence: high. (2026-10-20)
- Never mark an `agent_runs` row terminal (`completeAgentRun` done/failed/cancelled) before its `run_traces` doc is saved. Any reader that sees a terminal status (the PR timeline, a reload, `waitForPrRuns` in tests) then gets 404 from `GET /runs/:id/trace` in that window. This was the root cause of the `reviews.it` / `gitlab-feature-parity.it` flakes. Write the trace first on all three exit paths. Evidence: server/src/modules/reviews/run-executor.ts:82,357,418 (TRACE_BEFORE_STATUS); server/test/run-executor-trace-order.test.ts. Confidence: high. (2026-10-19)
- A per-IP "failed auth" limiter must never block a request that resolves to a valid principal, and must never count CSRF / role / owner rejections. The first version checked the block before resolving and counted every 401/403. A malicious page could then make a victim's browser fire 60 cross-site requests, each rejected by CSRF, and lock the whole office NAT out for a minute. Resolve the principal first, and count and block only a credential that was presented but did not resolve. Key IPv6 by /64, and fold IPv4-mapped forms, including the hex `::ffff:102:304`, into plain IPv4. Evidence: server/src/platform/auth/guard.ts:89 (`rejectionKey`), 265-271. Confidence: high. (2026-10-20)

- In `PrSyncCoordinator`, never call anything that can throw before releasing the single-flight slot in the last-resort `.catch` — a throwing `describeError` there left the repo "in flight" forever (no sync ever started again for it). Release `inflight.delete(repo.id)` first, and keep `describeError` wrapped so it can't throw. Evidence: server/src/modules/pulls/sync-coordinator.ts:72-80,185-189. Confidence: high. (2026-10-19)

## Codebase Patterns & Tool/Library Notes

- The `octokit` v4 bundle ships plugin-retry and plugin-throttling, which re-send a POST on 5xx and on rate limits. Removing our own `withRetry` therefore does NOT stop duplicate comment writes. Writes use a separate Octokit instance built with `retry: { enabled: false }, throttle: { enabled: false }`, wrapped in a `withRetry` that retries only 429 or a secondary rate limit. Tests count requests at the `fetch` level. Evidence: server/src/adapters/github/octokit.ts (`writeOctokit`); server/test/github-comment-retry.test.ts (PR #15). Confidence: high. (2026-10-20)
- It-tests share one Postgres cluster (a database per file, see server/test/global-setup.ts). Any query on a cluster-wide catalog (`pg_locks`, `pg_stat_activity`, `pg_terminate_backend`) must filter by `current_database()`, or it sees and kills other files' sessions. instance-claim.it did this before G7. Migration tests that need an unmigrated database use `startEmptyPg()`, not a raw `PostgreSqlContainer`. Evidence: server/test/instance-claim.it.test.ts; server/test/helpers/pg.ts. Confidence: high. (2026-10-20)
- Fastify does NOT run `onResponse` when the client aborts the socket, so a side effect there (an audit row after a committed mutation) is silently lost. Build the event and START the write in `onSend` (the last hook where the status is known). Make it fire-and-forget, track it in an in-flight set, and drain that set in `onClose` with a loop (`while (set.size) await Promise.allSettled([...set])`), so writes that start during shutdown are drained too. Evidence: server/src/platform/auth/audit-hook.ts:6,68,92. Confidence: high. (2026-10-20)

- Declare host-port members (`HostGitClient`, `HostCodeIndex`) as function-typed PROPERTIES (`clone: (repo: HostRepoRef, …) => …`), never method syntax. TS compares method parameters bivariantly, so with methods an implementation taking the wider `RepoRef` (or a narrowed `HostRepoRef` param) type-checks silently; property syntax makes `strictFunctionTypes` enforce it. The reverse upcast `HostGitClient` → legacy `GitClient` still compiles (GitClient uses methods, `adapters.ts` is do-not-touch) — never write it. Evidence: server/src/vendor/shared/host-git.ts:15-54. Confidence: high. (2026-10-19)
- Drizzle 0.38 `onConflictDoNothing({ target })` can't express an expression index target like `lower(full_name)`, so the GitLab repo insert is raw SQL with columns from `sql.identifier(col.name)`, and the partial-index predicate lives once in `reposIdentityWhere` (used by both the schema index `.where()` and the `ON CONFLICT … WHERE` arbiter). If the two drift, Postgres can't infer the arbiter and RAISES instead of DO NOTHING. Evidence: server/src/db/schema/repos.ts:22-27,68-71; server/src/modules/repos/repository.ts:155-176. Confidence: high. (2026-10-19)
- Drizzle's pg migrator runs ALL pending migrations in ONE transaction, so a `DO $$ … RAISE EXCEPTION … $$` guard in a migration (e.g. 0020 aborting on case-only duplicate repos) rolls back every pending migration cleanly — prefer abort-with-message over silently deleting data. Evidence: server/src/db/migrations/0020_cool_lucky_pierre.sql:16,22; node_modules/drizzle-orm/pg-core/dialect.js:60 (`session.transaction`). Confidence: high. (2026-10-19)

- `MockGitClient.readFile` returns `''` for missing files instead of throwing — code whose semantics are "throw ⇒ file absent" (e.g. the conventions config probe) must inject a custom fake GitClient in tests, or every probed path counts as present. Evidence: server/src/adapters/mocks.ts:293-294; server/test/conventions.it.test.ts:41-47. Confidence: high. (2026-08-19)

- The PR-list DTO (`GET /repos/:id/pulls`) is assembled in-handler with per-PR aggregates computed on READ via one IN-query + JS grouping (no FK denorm): latest-review SCORE from `reviews`, and total COST summed across the PR's `agent_runs`. `reviews.run_id` has NO FK to `agent_runs`. Add new list columns here, not in a repository. Evidence: server/src/modules/pulls/routes.ts:114-165. Confidence: high. (2026-07-31)
- `pnpm db:seed` creates a review (score 61) but NO agent_runs and no `reviews.run_id` — so run-level UIs (cost column, timeline, trace drawer) are empty on a fresh seed until a live review runs. The trace drawer additionally needs a `run_traces` doc (getRunTrace casts the jsonb, no zod parse). To demo run-level UIs offline, seed sample `agent_runs` + a `run_traces` row and link the review's run_id. Evidence: server/src/db/seed.ts (demo-runs block); server/src/modules/reviews/repository/run.repo.ts:183. Confidence: high. (2026-07-31)

## Decisions — with the why

- PR-list per-PR rollups (SCORE, FINDINGS) must aggregate across AGENTS, not pick "the latest review". A PR is typically reviewed by several agents at once, creating multiple `reviews` rows with the SAME `createdAt` — so `ORDER BY createdAt DESC` + first-seen returns an ARBITRARY agent (symptom: list showed score 100 / 0 findings while another agent had a blocker). Fix: take the latest review per `(prId, agentId)` (a re-run replaces, never double-counts), then SUM findings severities and take the MIN (worst) score across agents. Evidence: server/src/modules/pulls/routes.ts:114-176. Confidence: high. (2026-08-01)

## Recurring Errors & Fixes

- `rate-limit-per-user.test.ts` fails intermittently in the full suite but passes alone (~128 s). The sign-in tests send 21 REAL requests against a real 60 s `timeWindow`, and each `/auth/google/callback` takes about 1.5 s (waiting on OIDC I/O, ~0% CPU). Under load the 21 requests span more than 60 s, the window resets, and the expected 429 never comes. This is a pre-existing flake: rerun the file alone before debugging. Fix: a hermetic OIDC client and an injectable clock or fake timers. Evidence: server/test/rate-limit-per-user.test.ts:62; server/src/platform/auth/route-policy.ts:113 (`SIGN_IN_LIMIT`). Confidence: high. (2026-10-20)
- `pnpm arch` fails with "Your node version (23.x) is not supported" — dependency-cruiser only runs on `^20.12||^22||>=24`. Fix: run under an installed nvm Node 22, e.g. `PATH="$HOME/.nvm/versions/node/v22.14.0/bin:$PATH" pnpm arch`. Evidence: server/.dependency-cruiser.cjs; `~/.nvm/versions/node/`. Confidence: high. (2026-08-19)
- It-tests that insert their own repo hit `repos_ws_fullname_uq` if they reuse a seeded full_name — `seed()` already creates `acme/payments-api` in the default workspace. Use a unique `fullName` per test file (or a `repoSeq` counter like pulls-comments.it.test.ts:24). Evidence: server/src/db/seed.ts; server/test/conventions.it.test.ts:78. Confidence: high. (2026-08-19)
